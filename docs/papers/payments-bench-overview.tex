\housetitle{payments-bench}{An outbound transfer service that moves money exactly once}{Project overview}{\url{https://github.com/konradcinkusz/payments-bench}}{presents docs/OVERVIEW.md}

\begin{abstract}
\noindent
payments-bench is an outbound bank-transfer service built to show the mechanisms a payment rail
needs to move money exactly once and to recover when the bank on the other end misbehaves:
idempotent initiation, a six-state payment machine, a submit whose status is committed before the
partner call and whose failures become an Unknown outcome that is never retried blind, a resolver
and a background sweep that ask the partner before they act, a transactional outbox and an inbox,
a double-entry append-only ledger, and reconciliation that returns named breaks as a work queue.
The bank is simulated; the mechanisms are real code with tests. 365 tests pass against PostgreSQL
(\repopath{tests/}, counted by \texttt{dotnet test} on 2026-10-13), including ten scenario files run
end to end. Eighteen defects are recorded in the findings report, thirteen fixed, none caught by a
unit test failing on its own. Nine register rows are closed with proof and eighteen are open; the
first open one is that nothing here has ever talked to a real bank.
\end{abstract}

\section{Executive summary}

\finding{This is not a payments product. It is a bench for the mechanisms one depends on.}
Moving money is easy to get almost right. A transfer request arrives, a row is written, a call
goes to the bank, the bank says yes. Every one of those steps can happen twice, or half-happen, or
happen with nobody hearing the answer, and in each case naive code either loses track of a
customer's money or sends it twice. The repository builds the smallest service that handles those
cases on purpose, and writes down in a register which of them it has proved and which it has not.

What is on \texttt{main}:
\begin{itemize}[leftmargin=1.4em]
  \item an HTTP API (\repopath{src/PaymentsBench.Api}) to initiate (JSON or a \texttt{pain.001}
        file), list, submit, resolve and inspect a transfer, receive partner notifications, run
        reconciliation and read balances, behind bearer-token authentication;
  \item a six-state payment machine whose allowed moves are one table,
        \repopath{PaymentTransitions};
  \item idempotent initiation by \texttt{Idempotency-Key} plus a SHA-256 hash of the body, and
        optimistic concurrency in which one of two racing writers loses cleanly;
  \item a submit that commits \texttt{Submitted} before calling the partner and maps every
        failure after the request may have left the process to an \textbf{Unknown} outcome;
  \item a resolver that asks the partner by end-to-end id and resubmits only on
        \texttt{NotFound}, run on demand and by a background sweep;
  \item a transactional outbox with an at-least-once contract and a deduplicating consumer, and an
        inbox that deduplicates notifications;
  \item a double-entry, append-only ledger over \texttt{customer-funds},
        \texttt{pending-outbound} and \texttt{nostro};
  \item reconciliation of a day's statement (JSON or \texttt{camt.053}) as named breaks;
  \item scheme rules and dated holiday calendars as data under \repopath{scenarios/};
  \item a \textbf{simulated} partner bank with five fault profiles, and ten scenario files that run
        end to end in CI;
  \item PostgreSQL through migrations, a degraded in-memory mode, container images, a Fly.io
        topology that has never been deployed, a k6 load run and a security review.
\end{itemize}

The unit tests run against in-memory stores and a scripted partner, which is why the defects that
mattered were found by other means: walking a transfer through the running services over HTTP
(\finding{F-1}, \finding{F-2}), load runs (\finding{F-7}, \finding{F-9}), a scenario that should have
failed (\finding{F-8}) and a security review (\finding{F-14}); Section~\ref{sec:caught}.

\section{Why a payment rail is hard}

Four properties make outbound payments harder than ordinary request handling, and each maps to a
mechanism in the repository.

\begin{description}[leftmargin=1.4em,style=nextline]
  \item[Requests are repeated.] A client retries on a dropped connection, a queue redelivers, a
        user double-clicks. Without a stable notion of ``the same request'' each repeat is a new
        transfer. $\rightarrow$ idempotent initiation (Section~\ref{sec:idem}).
  \item[The partner's answer can be lost after the partner acted.] From the caller's side, a
        recorded transfer whose response was lost looks identical to a request that never
        arrived. A retry is safe in one case and a duplicate in the other, and the caller cannot
        tell which. $\rightarrow$ the Unknown outcome and the resolver
        (Section~\ref{sec:unknown}).
  \item[Delivery between systems is at least once.] Events and notifications can both arrive
        twice. $\rightarrow$ outbox and inbox (Section~\ref{sec:outbox}).
  \item[The money must be explainable afterwards.] ``Where is this customer's money right now''
        must have one answer derived from history, and what the bank's statement says must be
        compared with what the service believes. $\rightarrow$ the ledger
        (Section~\ref{sec:ledger}) and reconciliation (Section~\ref{sec:recon}).
\end{description}

Underneath sits a duller property: the schemes that carry the money have cut-offs, settlement
days and calendars that change independently of the code. $\rightarrow$ schemes as data
(Section~\ref{sec:schemes}).

\section{The money path}

Every movement of money is a balanced journal entry between three accounts. The postings for each
payment event are in one file, \repopath{src/PaymentsBench.Domain/Ledger/Postings.cs}, so the path
can be read top to bottom.

\begin{center}
\begin{tabular}{@{}llll@{}}
\toprule
Event & Posting & Debit & Credit \\
\midrule
Initiated & \texttt{Reserve} & \texttt{customer-funds} & \texttt{pending-outbound} \\
Settled & \texttt{Settle} & \texttt{pending-outbound} & \texttt{nostro} \\
Rejected (before settlement) & \texttt{Release} & \texttt{pending-outbound} & \texttt{customer-funds} \\
Returned (after settlement) & \texttt{Reverse} & \texttt{nostro} & \texttt{customer-funds} \\
\bottomrule
\end{tabular}
\end{center}

\begin{figure}[!htbp]
  \centering
  \includegraphics[width=0.82\linewidth,height=0.5\textheight,keepaspectratio]{\dgm{a1-money-path}}
  \caption{The money path: which payment event posts which movement between the three ledger
  accounts (\repopath{docs/diagrams/a1-money-path.mmd}).}
\end{figure}

Customer funds are reserved the moment a payment is initiated, sit in \texttt{pending-outbound}
while the transfer is in flight, and leave through \texttt{nostro} only when the partner says the
transfer settled. A rejection releases the reservation; a return reverses the settlement.
\finding{After reserve, settle and reverse, the customer's money is back where it started and
every account nets to zero}; the ledger test
\texttt{The\_full\_money\_path\_of\_a\_returned\_payment\_nets\_to\_zero\_on\_customer\_funds\_and\_nostro}
proves it.

Around them, \texttt{Iso20022} is the \texttt{pain.001} and \texttt{camt.053} edge (ADR 0014);

  \centering
  \includegraphics[width=0.82\linewidth,height=0.5\textheight,keepaspectratio]{\dgm{a6-delivery-topology}}
  \caption{What the composition root declares, and the degraded in-memory mode

\paragraph{Storage modes.} \repopath{InfrastructureRegistration} picks the stores once, at
start-up. With a connection string named \texttt{payments}, every store is EF Core on PostgreSQL,
the schema is a migration applied by a hosted service after the server starts, and every background
service waits on \texttt{MigrationGate} (ADR 0008). Without one, every store is in memory and the log
says at warning level that the service is running degraded. \finding{A missing database degrades
the service instead of stopping it}; the in-memory repository follows the same concurrency rule as
PostgreSQL, and has no outbox dispatcher.

\paragraph{Identity.} The API holds no signing key; it validates RS256 tokens against authservice's
JWKS (ADR 0015). Every endpoint needs a token except \texttt{/health} and \texttt{/alive}; the
partner webhook needs the \texttt{payments.partner.notify} grant, the ledger and reconciliation
\texttt{payments.operate} (ADR 0016). Anonymous calls are allowed in Development only, never on Fly.

\paragraph{Observability.} One OpenTelemetry trace per request with health probes filtered out;
\texttt{payments.transitions}, \texttt{payments.submitted.oldest\_age\_seconds} and
\texttt{payments.sweep.resolved} on the \texttt{PaymentsBench} meter; OTLP export, an opt-in
\texttt{/metrics}, and a provisioned Grafana dashboard.

\section{The seven rules}

\begin{center}
\begin{tabularx}{\linewidth}{@{}r X X@{}}
\toprule
\# & Rule & Enforced in \\
\midrule
1 & Submitted is committed before the partner call. & \texttt{SubmitPaymentHandler}: mark, update, outbox, commit, then call \\
2 & An unknown outcome is never retried. & \texttt{HttpPartnerGateway} maps failures to \texttt{Unknown}; \texttt{PartnerResilience.ShouldRetry} never retries a \texttt{POST} \\
3 & Resubmission needs the partner's word. & \texttt{ResolveSubmittedPaymentHandler}: only \texttt{NotFound}, same end-to-end id \\
4 & The ledger is append-only and balanced. & \texttt{JournalEntry} cannot be built unbalanced per currency \\
5 & Events through the outbox, notifications through the inbox. & every handler's unit of work; \texttt{IInbox.TryRecordAsync} first \\
6 & Reconciliation produces breaks, not alerts. & \texttt{ReconciliationReport} with named \texttt{BreakKind}s \\
7 & Scheme rules are data. & \repopath{scenarios/schemes.yaml}, \repopath{scenarios/calendars/} \\
\bottomrule
\end{tabularx}
\end{center}

Rules 1 to 3 are one argument and the core of the repository. \finding{If the state before the
call is durable, an unknowable result is never guessed at, and the only thing allowed to trigger
a second attempt is the partner's own statement that the first one does not exist, then a
transfer is sent at most once and is never lost track of.} \finding{F-2} is the evidence that
the argument holds even when the code around it is wrong.

% ----------------------------------------------------------------------------
\section{Idempotency}\label{sec:idem}

\texttt{POST /payments} requires an \texttt{Idempotency-Key} header; without it the API answers
400. \texttt{InitiatePaymentHandler} computes a SHA-256 over a canonical string of the fields that
make two requests the same request: end-to-end id, amount to two decimals in the invariant
culture, currency upper-cased, debtor and creditor accounts, and scheme. No payment with that key:
create one, reserve the funds and enqueue \texttt{PaymentInitiated} in one unit of work. Same key,
same hash: return the original. Same key, different hash: a 409. A \texttt{pain.001} file is read
into one command per transaction with a key built from its identifiers, so posting it twice
replays. Two identical requests racing each other: the unique index rejects the second, which gets
a 409, not the original 201 body (ADR 0013, R19). The key is global, not per caller (R21).

\section{The unknown outcome and the resolver}\label{sec:unknown}

ADR 0001 is the decision the repository is built around. A submit can fail in three ways that
look alike: the connection drops before the request lands, the request lands and the response is
lost, or the partner records the transfer and returns a 5xx. \finding{A naive retry creates a
second transfer in two of the three.}

\begin{figure}[!htbp]
  \centering
  \includegraphics[width=0.95\linewidth,height=0.5\textheight,keepaspectratio]{\dgm{a3-submit-resolve}}
  \caption{Submit and resolve: \texttt{Submitted} committed before the call; Accepted, Rejected
  and Unknown; the resolver asks by end-to-end id and resubmits only on \texttt{NotFound}
  (\repopath{docs/diagrams/a3-submit-resolve.mmd}).}
\end{figure}

\paragraph{Submit.} The handler moves the payment to \texttt{Submitted}, enqueues the event and
commits, and only then calls the partner. The gateway maps a 422 to \texttt{Rejected}; any other
non-success status, an empty body, a transport error, a timeout or an open circuit to
\texttt{Unknown}; a success with a partner reference to \texttt{Accepted}. \finding{On Unknown the
handler does nothing at all}: the payment stays at \texttt{Submitted}, the state that means ``ask
before you act''. \texttt{PartnerResilience.ShouldRetry} never retries a \texttt{POST}, so the
submit is sent once; it retries a \texttt{GET} on a transport error, an attempt timeout or a 5xx,
and never on an open circuit. That rule took two findings to reach (\finding{F-5}, \finding{F-9}).

\paragraph{Resolve.} If the payment is not at \texttt{Submitted}, the answer is
\texttt{AlreadyResolved}. Otherwise the resolver asks the partner by end-to-end id:
\texttt{NotFound} $\rightarrow$ resubmit once with the same end-to-end id, and \texttt{StillUnknown}
if that resubmit's own outcome is unknown (\finding{F-3}); \texttt{Accepted}, \texttt{Settled},
\texttt{Rejected} $\rightarrow$ apply it with its posting; \texttt{Unavailable} (open circuit,
timeout, transport failure, 5xx) $\rightarrow$ write nothing and answer \texttt{PartnerUnavailable};
\texttt{Returned} $\rightarrow$ refuse. \finding{Unavailable is never read as NotFound}: that is
what keeps an outage from becoming a resubmit, and before it existed the resolver answered 500
during an outage (\finding{F-7}). The same end-to-end id lets the partner recognise a late first
attempt as a duplicate, an assumption stated in ADR 0001 that the simulated partner honours.

\paragraph{The sweep.} \texttt{SubmittedPaymentSweeper} runs the same resolver every 30\,s over
Submitted payments older than 60\,s, oldest first, at most 50 at a time (ADR 0011). It never calls
the partner itself, so ADR 0001 holds by construction. Its alert is documented, not deployed (R17).

\section{Outbox and inbox}\label{sec:outbox}

Every handler enqueues the payment's domain events through \texttt{IOutbox} in the same unit of
work as the state change and the ledger entry. With PostgreSQL, the dispatcher publishes
undispatched rows in \texttt{OccurredAt} order and marks a row dispatched only after its publish
returned: \finding{delivery is at least once by design}. \texttt{Outbox:Publisher} selects a log
line (the default) or an in-process channel with a \texttt{DedupingConsumer} that applies each
message id once; the contract is proved against PostgreSQL (ADR 0010). \finding{No broker has ever
carried an event} (R5). In the in-memory mode there is no dispatcher at all.

Partner notifications, which need the \texttt{payments.partner.notify} grant, are recorded in
\texttt{IInbox} by notification id before anything else; a second delivery returns
\texttt{Duplicate} and changes nothing. A notification for an unknown end-to-end id is recorded and
reported as \texttt{UnknownPayment}, not dropped. The sender is a bearer-token client, not a
signing partner (R13).

\section{The ledger}\label{sec:ledger}

ADR 0002: every money movement is a \texttt{JournalEntry} of at least two lines that balance per
currency; entries are appended, never updated or deleted; a correction is another entry; balances
are sums over lines; direction is the side, never a negative amount. The ledger tests, in memory and against
PostgreSQL, prove that
an unbalanced entry cannot exist, that balance is per currency, that direction is the side, that a
rejection releases the reservation, and that a returned payment nets to zero. Balances are sums
over rows; at volume that needs a materialised balance maintained by the same entries, which stay
the source of truth.

% ----------------------------------------------------------------------------
\section{Reconciliation}\label{sec:recon}

ADR 0003: a statement that disagrees with the ledger is the normal case on some days, and an
alert saying ``reconciliation failed'' tells the person on call nothing. The service reads the day's
statement as JSON or, with \texttt{Partner:StatementFormat} set to \texttt{camt053}, as an ISO 20022
\texttt{camt.053} document, and matches its debit lines to the payments that settled with that value
date, whatever happened to them since, by end-to-end id and exact amount and currency, and returns the number matched and a list of breaks, each with both
amounts where both exist.

\begin{center}
\begin{tabularx}{\linewidth}{@{}l X@{}}
\toprule
Break kind & Meaning \\
\midrule
\texttt{OnStatementOnly} & the statement books a movement with no settled payment behind it \\
\texttt{InLedgerOnly} & a payment settled that the statement does not show \\
\texttt{AmountMismatch} & both sides have it, with different amounts \\
\bottomrule
\end{tabularx}
\end{center}

\begin{figure}[!htbp]
  \centering
  \includegraphics[width=0.85\linewidth,height=0.5\textheight,keepaspectratio]{\dgm{a5-reconciliation}}
  \caption{Reconciliation as a work queue (\repopath{docs/diagrams/a5-reconciliation.mmd}).}

``Whatever happened since'' is the fix for \finding{F-4}: a payment settled on a day and returned
later used to be an \texttt{OnStatementOnly} break for its settlement day. The return day itself
still cannot reconcile, because the simulated statement has no credit line for the return (R18),
and the \texttt{camt.053} samples are hand-written, not a bank's (R20).

\section{The partner simulator and the scenario classes}

\finding{The partner is a simulated bank whose API shape is invented} (R1). It accepts transfers
(deduplicated by end-to-end id), answers lookups, lets a test settle or return a transfer, serves
a statement per date, and switches its fault profile at runtime: \texttt{None},
\texttt{Latency} (1,500\,ms by default), \texttt{TimeoutAfterAccept} (records the transfer, holds
the response 10,000\,ms by default), \texttt{ServerError} (503, records nothing),
\texttt{RejectAll} (422, \texttt{AC01} by default), \texttt{StatementDrift} (0.01 by default added
to every statement amount).

Because it deduplicates by end-to-end id, it cannot count submissions, so ``no duplicate
transfer'' under load is checked indirectly (\finding{F-15}, R15).

Ten scenario files in four classes describe what the rail must survive, as data: \texttt{happy}
(3), \texttt{partner-failure} (3), \texttt{duplicate} (2), \texttt{reconciliation} (2).
\finding{They run}: \repopath{tests/PaymentsBench.Scenarios} discovers every file and runs it end to
end, in process, against a fresh API and simulator pair, in memory and on PostgreSQL, asserting
every expected key (ADR 0012); CI gates on it, and R3 is closed. It exercises real HTTP
serialisation and the real resilience pipeline without a socket, and no process boundary or real
clock. One of its own defects, a timeout scenario that passed without its timeout
(\finding{F-8}), is why the runner now tests itself.

\section{Production readiness, honestly}

\begin{itemize}[leftmargin=1.4em]
  \item \textbf{The partner is simulated} (R1); the ISO 20022 samples are hand-written and not
        schema-validated (R20).
  \item \textbf{Nothing has been deployed} (R14), and the deployment's security settings are
        unverified (R26).
  \item \textbf{Payments have no owner}; the idempotency key and end-to-end id are global (R21, R22).
        Deploy single-operator only until R21 closes. No rate limiting (R23), no operator separation
        or audit trail (R24), hostile input only partly bounded (R25).
  \item \textbf{The webhook trusts a bearer token}, not a partner signature (R13).
        \textbf{No broker has carried an event} (R5).
  \item \textbf{The load numbers are in memory, one instance, anonymous} (R15). \textbf{The sweep's
        alert is prose} (R17). \textbf{The value date is not stamped at submission} (R11).
        \textbf{A return day does not reconcile} (R18). \textbf{A concurrent duplicate initiate is a
        409} (R19). \textbf{The integration fixture's Docker path is untested} (R12).
  \item \textbf{No sanctions, AML or limits} (R10), by scope.
\end{itemize}

\section{Decisions and non-goals}

Sixteen decision records (\repopath{docs/adr/}). The ones the argument rests on: \textbf{0001}, an
unknown submit outcome is never retried blind; \textbf{0002}, money is a double-entry, append-only
ledger; \textbf{0003}, reconciliation produces breaks, not alerts; \textbf{0011}, Submitted payments
are swept, never blindly resubmitted; \textbf{0013}, optimistic concurrency by remembered version.
The others record calendars as data (0007), migrations behind a gate (0008), validation and errors
(0009), the outbox contract (0010), scenarios in process (0012), ISO 20022 at the edge (0014),
identity (0015, 0016), and this documentation (0004 to 0006).

Non-goals: being a payments product; talking to a real bank or a real broker; compliance controls (R10); inbound
payments, FX, fees and netting; fuzzy reconciliation (anything else is a new, named break kind).

\section{Relationship to the standards}

The repository conforms to architecture-standards \cite{standards} and does not re-derive it. Its
documentation follows agent-eval-bench \cite{aeb}: a long-form overview as the source of truth, a
findings report written to be unflattering, a register of what is not proved, and presentation
editions, like this one, that add nothing the overview does not contain.

\section{Reproducibility}

Every number in this document is reproducible from the repository at the commit this PDF was
built from.

\begin{verbatim}
git clone https://github.com/konradcinkusz/payments-bench
cd payments-bench
PAYMENTSBENCH_TEST_POSTGRES="Host=localhost;Port=5432;Username=postgres" \
  dotnet test               # 365 tests; needs a PostgreSQL that trusts you
npm ci                      # pinned doc tooling, including mermaid-cli
npm run lint                # markdown, links, diagrams, papers
npm run render:diagrams     # docs/diagrams/*.mmd -> docs/diagrams/rendered/*.pdf
cd docs/papers && latexmk -pdf payments-bench-overview.tex
\end{verbatim}

The walk-through behind F-1 and F-2 is the README's ``Run it'' section: start
\texttt{PaymentsBench.PartnerSimulator} and \texttt{PaymentsBench.Api} without a database, then
initiate, submit under \texttt{TimeoutAfterAccept}, resolve, settle, notify twice and reconcile with
\texttt{curl}. The k6 load run is \texttt{scripts/load-test.sh} (\repopath{k6/README.md}); its
numbers, and what they do not prove, are in the register.
