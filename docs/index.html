payments-bench · outbound bank transfers · simulated partner

Move money exactly once, and say what is not yet proved.

payments-bench is an outbound bank-transfer service built to show the mechanisms a payment rail needs when the bank on the other end misbehaves: idempotent initiation, a state machine with one table of allowed moves, an unknown-outcome rule that never retries blind, a double-entry ledger, and reconciliation that produces a work queue. It is a bench, not a product.

The partner bank is simulated. Nothing in this repository has talked to a real bank. The partner is src/PaymentsBench.PartnerSimulator, and its API shape is invented (register row R1, below).

double-entry ledger

The money path

Customer funds sit in customer-funds until a transfer is initiated, in pending-outbound while it is in flight, and leave through nostro only when the partner says it settled. Every movement is a balanced, append-only journal entry; balances are sums, never columns.

The seven rules that matter

1. Submitted is committed before the partner call

A crash between the commit and the response leaves a payment at Submitted: the state that means “ask before you act”.

2. An unknown outcome is never retried

Timeouts, dropped connections and 5xx after the body was sent map to SubmitOutcome.Unknown. The HTTP resilience pipeline retries GET only.

3. Resubmission needs the partner’s word

Only PartnerStatus.NotFound allows a second submit, with the same end-to-end id.

4. The ledger is append-only and balanced

A JournalEntry that does not balance per currency cannot be constructed. Balances are sums, never columns.

5. Outbox out, inbox in

Publishing is at least once; consumers dedupe on the message id.

6. Reconciliation produces breaks, not alerts

Three kinds, each with the two amounts, so the person working the queue has what they need on the row (ADR 0003).

7. Scheme rules are data

Cut-off, currency and settlement days per scheme live in scenarios/schemes.yaml; code reads them.

Each file under scenarios/ describes one thing the rail must survive: the fault the simulated partner injects, the calls made, and the state the system must end in.

R12026-10-13Nothing here has ever talked to a real bank. The partner is PaymentsBench.PartnerSimulator; its API shape is invented, not SEPA, Faster Payments or SWIFT.A gateway implementation against a real or sandbox scheme API exists and one scenario runs against it.
R22026-10-13No ISO 20022 message is parsed or produced. The statement is a JSON reduction of what camt.053 carries; initiation is a JSON body, not pain.001.pain.001 out and camt.053 in, with a round-trip test on real sample files.
R32026-10-13The scenario files are a specification, not an executed suite. ScenarioFilesTests checks they parse; no runner drives them against the API and the simulator.tests/PaymentsBench.Scenarios executes every file end to end and CI gates on it.
R52026-10-13The outbox dispatcher publishes to a log line. No broker is wired; at-least-once delivery to a consumer is a design claim.An IEventPublisher against a real broker, and a consumer-side dedupe test.
R62026-10-13Concurrency is a column, not a test. Version is a concurrency token; no test races two writers on one payment.A test that proves one of two concurrent updates fails with a concurrency exception.
R82026-10-13The resolver is called, never scheduled. POST /payments/{id}/resolve exists; nothing sweeps Submitted payments older than N seconds on its own.A background sweep with a metric on the age of the oldest Submitted payment, and an alert threshold documented.
R92026-10-13No load, no chaos. Nothing has measured throughput, and the simulator's faults are set by hand, not injected randomly under load.A k6 or equivalent run with the simulator cycling fault profiles, and numbers in this file.
R102026-10-13Sanctions, AML, limits: absent. The service moves any amount to any account.Out of scope for the bench; stays open as a statement of scope.
R112026-10-13The computed value date is not stamped on the payment. ValueDateCalculator and the per-scheme HolidayCalendar exist and are tested, but nothing calls them at submit or acceptance; Payment.ValueDate is still set only when the partner reports settlement (or defaults to today's date). The calendars are proved; the value date a customer is shown at submission is not.SubmitPaymentHandler (or acceptance) computes the value date from the scheme's rules and calendar, stamps it on the payment (a domain and schema change), and a test pins it for a known closing day.
R122026-10-13The Testcontainers path of the integration fixture has not run, and concurrent migration is untested. CI and local runs use PAYMENTSBENCH_TEST_POSTGRES; the fallback that starts postgres:16-alpine through Docker was only seen failing loudly. Several instances migrating at once rely on EF Core's migration lock.A run on a machine with Docker and no env var, and a test that starts two migrations against one database.
R132026-10-13The partner webhook is authenticated with a bearer token, not a partner signature. /partner/notifications falls under the API's fallback policy, so the sender needs a token from authservice; a real partner would sign the payload (HMAC) or present a client certificate (mTLS), and nothing here verifies either.Partner notifications are verified by a partner-held key (signature or mTLS) and a test rejects an unsigned one.

Run it

No bank is involved: the partner is the simulator. Without a payments connection string the service runs in memory and says so in its log.

  1. Run the tests. 142 tests.

    dotnet test
    README.md 30 in tests/PaymentsBench.Domain.Tests + 42 in tests/PaymentsBench.Application.Tests + 31 in tests/PaymentsBench.Integration.Tests + 39 in tests/PaymentsBench.Api.Tests · 2026-10-13

  2. Start the simulated partner and the API, in two terminals.

    dotnet run --project src/PaymentsBench.PartnerSimulator   # http://localhost:5101
dotnet run --project src/PaymentsBench.Api                # http://localhost:5100

    Or, with Aspire (PostgreSQL, simulator, API, dashboard): dotnet run --project src/PaymentsBench.AppHost

  3. Initiate and submit a transfer. The Idempotency-Key header is required.

    curl -X POST localhost:5100/payments -H 'Content-Type: application/json' -H 'Idempotency-Key: demo-1' \
  -d '{"endToEndId":"E2E-1","amount":100.00,"currency":"EUR","debtorAccount":"DE89...","creditorAccount":"GB33...","scheme":"sepa"}'
curl -X POST localhost:5100/payments/<id>/submit

  4. Make the simulated partner time out after accepting, then watch the resolver recover without a duplicate.

    curl -X PUT localhost:5101/faults -H 'Content-Type: application/json' -d '{"kind":"TimeoutAfterAccept","delayMilliseconds":8000}'
curl -X POST localhost:5100/payments/<id>/submit      # -> Submitted (outcome unknown)
curl -X PUT localhost:5101/faults -H 'Content-Type: application/json' -d '{"kind":"None"}'
curl -X POST localhost:5100/payments/<id>/resolve     # -> {"outcome":"Accepted"}, one transfer at the partner

  5. Settle, notify (twice: the second is a duplicate), reconcile, read the ledger.

    curl -X POST 'localhost:5101/transfers/E2E-1/settle?valueDate=2026-10-14'
curl -X POST localhost:5100/partner/notifications -H 'Content-Type: application/json' \
  -d '{"notificationId":"N-1","endToEndId":"E2E-1","kind":"Settled","valueDate":"2026-10-14"}'
curl -X POST localhost:5100/reconciliation/runs/2026-10-14
curl localhost:5100/payments/<id>/ledger
