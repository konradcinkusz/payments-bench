payments-bench · outbound bank transfers · simulated partner

Move money exactly once, and say what is not yet proved.

payments-bench is an outbound bank-transfer service built to show the mechanisms a payment rail needs when the bank on the other end misbehaves: idempotent initiation, a state machine with one table of allowed moves, an unknown-outcome rule that never retries blind, a double-entry ledger, and reconciliation that produces a work queue. It is a bench, not a product.

The partner bank is simulated. Nothing in this repository has talked to a real bank. The partner is src/PaymentsBench.PartnerSimulator, and its API shape is invented (register row R1, below).

double-entry ledger

The money path

Customer funds sit in customer-funds until a transfer is initiated, in pending-outbound while it is in flight, and leave through nostro only when the partner says it settled. Every movement is a balanced, append-only journal entry; balances are sums, never columns.

The seven rules that matter

1. Submitted is committed before the partner call

A crash between the commit and the response leaves a payment at Submitted: the state that means “ask before you act”.

2. An unknown outcome is never retried

Timeouts, dropped connections and 5xx after the body was sent map to SubmitOutcome.Unknown. The HTTP resilience pipeline retries GET only.

3. Resubmission needs the partner’s word

Only PartnerStatus.NotFound allows a second submit, with the same end-to-end id.

4. The ledger is append-only and balanced

A JournalEntry that does not balance per currency cannot be constructed. Balances are sums, never columns.

5. Outbox out, inbox in

Publishing is at least once; consumers dedupe on the message id.

6. Reconciliation produces breaks, not alerts

Three kinds, each with the two amounts, so the person working the queue has what they need on the row (ADR 0003).

7. Scheme rules are data

Cut-off, currency and settlement days per scheme live in scenarios/schemes.yaml; code reads them.

R12026-10-13Nothing here has ever talked to a real bank. The partner is PaymentsBench.PartnerSimulator; its API shape is invented, not SEPA, Faster Payments or SWIFT.A gateway implementation against a real or sandbox scheme API exists and one scenario runs against it.
R52026-10-13, narrowed 2026-10-13No broker has ever carried an event. The default publisher writes a log line. The at-least-once contract and consumer-side dedupe are proved in process, against PostgreSQL, with a bounded channel standing in for the broker: OutboxContractTests (an event enqueued with a payment change is delivered once with the outbox row id as message id; a publish whose dispatched mark is lost is republished with the same id and the consumer applies it once and counts one duplicate; OccurredAt order; nothing published for a failed commit), DedupingConsumerTests, OutboxPublisherSelectionTests. The channel is not durable and shows nothing of broker acknowledgement, redelivery timing or partitioning. In-memory (degraded) mode has no dispatcher at all. See ADR 0010.An IEventPublisher against a real broker, run through the same contract tests.
R102026-10-13Sanctions, AML, limits: absent. The service moves any amount to any account.Out of scope for the bench; stays open as a statement of scope.
R112026-10-13The computed value date is not stamped on the payment. ValueDateCalculator and the per-scheme HolidayCalendar exist and are tested, but nothing calls them at submit or acceptance; Payment.ValueDate is still set only when the partner reports settlement (or defaults to today's date). The calendars are proved; the value date a customer is shown at submission is not.SubmitPaymentHandler (or acceptance) computes the value date from the scheme's rules and calendar, stamps it on the payment (a domain and schema change), and a test pins it for a known closing day.
R122026-10-13The Testcontainers path of the integration fixture has not run, and concurrent migration is untested. CI and local runs use PAYMENTSBENCH_TEST_POSTGRES; the fallback that starts postgres:16-alpine through Docker was only seen failing loudly. Several instances migrating at once rely on EF Core's migration lock.A run on a machine with Docker and no env var, and a test that starts two migrations against one database.
R132026-10-13The partner webhook is authenticated with a bearer token, not a partner signature. /partner/notifications falls under the API's fallback policy, so the sender needs a token from authservice; a real partner would sign the payload (HMAC) or present a client certificate (mTLS), and nothing here verifies either.Partner notifications are verified by a partner-held key (signature or mTLS) and a test rejects an unsigned one.
R142026-10-13Nothing has been deployed. The Fly.io topology (flyio/), the tag-driven workflow (deploy.yml) and docs/DEPLOYMENT.md exist and the configs validate offline, but no tag has deployed the estate: no image has been pulled by Fly, the first-boot database script and the post-deploy JWKS and 401 checks have never run, and the cost figures are list prices, not an invoice.A tag deploys the estate (postgres, authservice, the simulated partner, the API) and one authenticated payment is walked against the public URL.
R152026-10-13The load numbers are in memory, on one machine, anonymous. The run in [Load numbers](#load-numbers-r9) used in-memory stores (no PostgreSQL), one API instance, one simulator, loopback networking, and the Development policy that allows anonymous calls. It says nothing about PostgreSQL under load, the authenticated path, or more than one instance. The simulator also cannot report how many times a transfer was submitted (it keys transfers by end-to-end id and answers a repeat with the existing one), so "no duplicate transfers" is checked only through duplicate_payments and simulator_mismatches, not by counting submissions at the partner.The same k6/payments.js run against PostgreSQL with the authenticated path (authservice), on at least two API instances, plus a submission counter on the simulator so duplicate transfers are counted where they would occur.
R172026-10-13The sweep is proved in process, and its alert is prose. SweepSubmittedPaymentsTests drive the sweeper over in-memory stores and a scripted partner; the one PostgreSQL test covers the query, not a sweep over EF stores under two instances. ADR 0011 documents the alert threshold, but no alert rule is deployed. Payments that stay StillUnknown or PartnerUnavailable keep the front of the oldest-first queue and starve younger ones past BatchSize; two instances may race for one payment and one counts a failed.A sweep runs on the EF stores in tests/PaymentsBench.Integration.Tests with two sweepers on one database, the alert is a rule in the deployment, and the starvation case is tested or removed (for example by ordering on last attempt).
R182026-10-13A return has no statement line of its own. F-4 is fixed for the settlement day (a payment settled on a day and returned since still matches that day's debit), but the simulated statement carries no credit for the return itself, so the return day cannot reconcile, and the return-after-settlement scenario reconciles the settlement day only.The simulator books a credit line on the return's value date, ReconciliationService matches it to the returned payment, and return-after-settlement reconciles both days with no break.
R192026-10-13A concurrent duplicate initiate returns 409, not the original 201 body. Two requests with one idempotency key racing past the existence check both insert; the unique index rejects the second, which becomes ConcurrencyConflictException and a 409 (ADR 0013). A sequential replay still returns the original payment.A decision to replay the stored response to the loser, with a test that races two identical initiations and sees the same 201 body twice.
R202026-10-13The ISO 20022 samples are ours, not a bank's. The documents under tests/PaymentsBench.Iso20022.Tests/samples/ (a pain.001.001.09 with two transactions, one with an unmapped service level, a camt.053.001.08 with three entries) are hand-written in the published message shape with fictitious parties and the standard example IBANs. They are not validated against the official XSDs, and none is a file issued by a bank, so the readers accept what we believe the schema says, nothing more. The writers leave out what the internal model does not hold (party names, balances), so their output is not schema-complete. The gateway still submits JSON to the simulated partner (POST /transfers); pain.001 is read at our API's edge and never leaves it, and the statement is JSON unless Partner:StatementFormat is camt053.The samples and the writers' output are validated against the official pain.001.001.09 and camt.053.001.08 XSDs in CI, and one bank-issued sample is read.

R162026-10-13POST /payments/{id}/resolve answered 500 when the partner circuit was open. R62026-10-13Concurrency was a column, not a test. R272026-10-13An open partner circuit was retried, so resolve and every sweep waited out the retry backoff before answering PartnerUnavailable. Run it

No bank is involved: the partner is the simulator. Without a payments connection string the service runs in memory and says so in its log.

  1. Run the tests. 318 tests.

    dotnet run --project src/PaymentsBench.PartnerSimulator   # http://localhost:5101

  3. Initiate and submit a transfer. The Idempotency-Key header is required.

    curl -X POST localhost:5100/payments -H 'Content-Type: application/json' -H 'Idempotency-Key: demo-1' \
  -d '{"endToEndId":"E2E-1","amount":100.00,"currency":"EUR","debtorAccount":"DE89...","creditorAccount":"GB33...","scheme":"sepa"}'
curl -X POST localhost:5100/payments/<id>/submit

  4. Make the simulated partner time out after accepting, then watch the resolver recover without a duplicate.

    curl -X PUT localhost:5101/faults -H 'Content-Type: application/json' -d '{"kind":"TimeoutAfterAccept","delayMilliseconds":8000}'
curl -X POST localhost:5100/payments/<id>/submit      # -> Submitted (outcome unknown)
curl -X PUT localhost:5101/faults -H 'Content-Type: application/json' -d '{"kind":"None"}'
curl -X POST localhost:5100/payments/<id>/resolve     # -> {"outcome":"Accepted"}, one transfer at the partner

  5. Settle, notify (twice: the second is a duplicate), reconcile, read the ledger.

    curl -X POST 'localhost:5101/transfers/E2E-1/settle?valueDate=2026-10-14'
curl -X POST localhost:5100/partner/notifications -H 'Content-Type: application/json' \
  -d '{"notificationId":"N-1","endToEndId":"E2E-1","kind":"Settled","valueDate":"2026-10-14"}'
